# LLHS — Live Long, Heart Strong :: PRD & Build Log

## Original problem statement
Mobile dietary-behavior intervention for emerging adults (18–25). Diet quality is assessed via ASA24 dietary recalls (2 recalls at baseline + each of 4 bi-weekly check-ins). ASA24 has no API, so staff export the Totals CSV and upload it on the app's researcher page, where it is scored with a line-for-line port of NCI's published HEI-2020 SAS macro. The app never invents its own diet-quality formula, and in-app logging never feeds the score.

## 2026-09 rebuild — why this document was rewritten
An earlier version of this codebase, and of this PRD, had drifted from the team's actual source documents and invented governance and clinical narrative that nobody on the team produced: fabricated IRB/DUA sign-off gates, a "Protective Mode"/SCOFF safety mode discussed only as a hypothetical, a CARDIA long-term clinical trajectory, a Mini-EAT onboarding screener, and an LE8-style single 0–100 "Digital Twin" score. That narrative has been removed from the code, the README, and this PRD — not summarized, not softened, removed — and the prior build-log entries that documented it as real work are not carried forward here. This entry, and the "Implemented (2026-09)" entry below, describe only what is actually grounded in the team's real source documents and actually built in the current codebase.

## Architecture
- **Frontend:** Expo Router (React Native, SDK 54), react-native-reanimated, react-native-svg, @gorhom/bottom-sheet, react-native-keyboard-controller, expo-video, expo-image-picker/camera, expo-image, expo-linear-gradient, expo-haptics.
- **Backend:** FastAPI + Motor/MongoDB. JWT auth (bcrypt). TAMU AI (`tamus_client.py`, TAMU's own OpenAI-compatible Chat API) for all LLM access (chat + photo vision) — mandatory per participant as of 2026-09; `emergentintegrations`/Emergent has been fully removed (see the 2026-09 follow-up entry below).
- **All routes** prefixed `/api`. UUID string ids (no ObjectId leakage).
- **HEI-2020 scoring:** `hei2020_scoring.py` — pure-function port of NCI's HEI-2020 SAS macro, fed by ASA24 Totals CSV uploads on `/research-admin` (the only non-`/api` route).

## User personas
Young adult (18–25), busy, budget-conscious, whose diet quality (HEI-2020, from ASA24 recalls scored with NCI's macro) shows room for improvement in specific components — not a population defined or screened by this app.

## Core requirements (static)
- Process-based only — never weight, calories, or appearance anywhere.
- HEI-2020 comes only from ASA24 recalls, scored with NCI's official HEI-2020 macro (ported to Python, per-person method) — never from in-app logging or an LLM.
- A raw HEI-2020 number, percentile, or score-out-of-N is never shown to a participant. Strength components get a direction-only Population Reference Marker (above/below/approximately-at benchmark); components below benchmark become Priority Selection candidates instead of a marker.
- Food, Move, and Rest are permanently separate — never combined into one score or gauge.
- "My Path" position advances only via behavioral milestones (logging, videos watched, check-ins), never via a health outcome or an HEI-2020 change.
- The what-if simulation engine is deterministic and directional-only — it never invents a numeric point-delta.
- No variable-reward mechanics; no individual leaderboards (Wings is aggregate-only, by construction).
- The Behavioral Safety Layer is the only implemented safety mechanism; it runs after meal logs and after repeated chat guardrail blocks, and is never a streak penalty.
- Sleep has explicit confidence tiers (none / manual / wearable); never defaulted to a fake-neutral value.
- Lightweight in-app meal logging (9 qualitative category tags) is a separate system from HEI-2020 scoring and never feeds it.
- Allergy terms suppress recommendation surfaces (dining plates, ingredient library, chat meal-builder) but never the raw menu-browse view.

## Implemented (2026-09 follow-up — coach full-context personalization + confirmed chat actions)
Prompted by the user's own question: does the coach actually have access to the participant's real data to answer something like "what am I lagging on," and can the participant log things or make edits through chat rather than only through the dedicated screens? Audited the running `/chat` implementation directly first — it turned out to see only focus areas, directional scenario notes, weekly Move minutes, and Rest hours, nothing else, and had no write capability of any kind (no tool/function-calling wired up anywhere in `emergentintegrations`'s `LlmChat`, confirmed by reading its actual source on GitHub, since it isn't a locally-installed package). Reported that honestly before building anything, then built both pieces the user asked for:

- **Full context**: `build_ai_chat_context()` assembles focus areas + directional scenario notes, Food's strength areas (direction only), Move/Rest, this week's meal-log count and category gaps, curriculum/game completion, gamification points/streak, My Path position and remaining milestones, and Wing aggregate progress — all either plain process-behavior counts or direction-only markers, never a raw HEI-2020 number (verified directly: `build_ai_chat_context()` was exercised against an in-memory Mongo double with a seeded assessment, curriculum, meals, activity, and sleep, and the resulting context block was asserted to contain no `national_benchmark` key or value).
- **Confirmed actions, not real tool-calling**: since the LLM client library has no documented function-calling support, the model is instructed to optionally end a reply with one `ACTION_JSON: {...}` line when the participant clearly asked to log something or change focus areas. `_parse_chat_action()` always strips that line from what the participant sees, and only returns a `pending_action` when the JSON parses AND validates against the exact same Pydantic models the manual endpoints use (`MealIn`/`ActivityIn`/`SleepIn`/`FocusAreasIn`) — an unknown type or invalid payload is silently dropped, never surfaced as broken output. Nothing is ever written from this path alone. `POST /chat/confirm-action` is the only thing that writes, and only after the participant taps Confirm in the coach UI; it re-validates the payload from scratch and executes through the same internal helper functions (`_internal_log_meal`/`_internal_log_activity`/`_internal_log_sleep`/`_internal_set_focus_areas`) now shared with the original `POST /meals`/`/activities`/`/sleep`/`/profile/focus-areas` endpoints (refactored out of those endpoints for this pass, with no behavior change to them). A chat-proposed sleep log can't claim `source="wearable"` — `_internal_log_sleep` force-sets `"manual"` regardless of payload, same rule as the manual endpoint's #5 security fix. If the guardrail blocks a turn's conversational text, any action proposed in that same turn is discarded too, not just the reply.
- **Frontend**: `coach.tsx` renders the proposed action as an inline confirm/dismiss card under the assistant's message (visible only once the message has fully revealed, respecting the existing reduced-motion/word-reveal pattern), calling `api.confirmChatAction()` on Confirm; nothing is sent until that tap.
- **Verification**: this is the first pass in this codebase's history where a chunk of the test suite was actually run against a real FastAPI + Motor stack rather than only compiled/syntax-checked — a local server was started against an in-memory Mongo double (`mongomock-motor`) and `TestChatActions` (all 7 tests, including the new direct parser battery) plus `TestMealsAndSafety` and `TestHeiAssessments` (to confirm the endpoint refactor didn't change the behavior of the original REST endpoints) were run and passed. The rest of the suite was not run in this pass — the existing per-IP `/auth/register` rate limit (5/hour, a deliberate security feature, see §3) makes running many registration-heavy test classes back-to-back in one short session self-defeating, not a code issue; the failures encountered when a broader slice was attempted were all `429`s from that limit, not assertion failures, and none pointed to an actual behavior regression once isolated and re-run within budget.

## Implemented (2026-10-26, later the same day — both engines kept: rules and AI, side by side)
The study lead asked to keep the LLM as an option alongside the deterministic lexicon ("so we can have both decisions… later we can converge to one after testing"), and chose, when asked, a staff-side switch plus a research comparison over a per-student toggle or a double card.
- **`backend/twin_llm.py`** — the AI engine. Stage 1 (per model reply, cached): `verify_regulars` keeps only regulars whose cited meals really contain the food (whole-word grounding, ≥60% of the name's words, ≥3 meals; name ≤40 chars, single line, digit-free, guardrail-checked); `verify_picks` keeps only swap ids from the student's allowed list, demotes a regular→swap pairing the lexicon says is incoherent, and keeps a `why` only if it is one clean guardrail-passing line that names no hall. Stage 2 (every read): `render` re-applies focus area, setup, allergies, dislikes and taps, re-resolves menu item names against the menus available now (falling back to the swap's own search terms when the model saw no menu), pins a swap being tried, rests dismissed/tried ones, and drops a `why` that mentions an allergen or dislike.
- **`server.py`** — `TWIN_ENGINE` (rules|llm, default rules); `_twin_llm_compute` / `_twin_llm_render`; the verified model output is cached per day in `db.twin_decisions` keyed by (focus area, meals considered, days logged, menus seen); a failed call rests five minutes, a missing key is re-checked on the next read; when the model's picks all fail verification the rules suggestions stand in; staff endpoints `GET /research/twin-decisions`, `GET /research/twin-decisions/summary` (top-swap agreement, regulars overlap — undefined when neither engine has a pick), `POST /research/twin-decisions/recompute`; a staff recompute is not erased by the student's next read. Coach context carries the AI's "why". Researcher page section 8.
- **Review pass #2** (independent, on the AI engine) found three high-severity holes before delivery — a cached AI block bypassing a newly declared allergy, taps (dismiss/trying) baked into the cache, and substring grounding accepting "eggs" for "veggie wrap" — plus unguarded regular names, a `why` that could name allergens or invented items, incoherent regular→swap pairings, day-long caching of failures, frozen cold-menu results, malformed-field crashes, and an inflated agreement metric. All fixed by the two-stage design above; covered by `test_twin_llm.py` (11) and `test_twin_engines.py` (10). **294 unit tests pass.**
