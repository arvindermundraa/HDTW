# Live Long, Heart Strong (LLHS)

A mobile app-based dietary-behavior intervention for emerging adults (18–25), grounded in an externally-scored **HEI-2020** diet-quality index and organized around three permanently separate domains — **Food, Move, and Rest** — plus a single fixed-appearance "My Path" progress trail that advances only on logging behavior, never on a health outcome.

**This document describes the rebuilt app** (September 2026), grounded directly in the project's source documents: the DTL "App Review and Development Notes," the "Updated DTL Slides 9.10.26," the onboarding Nutrition & Lifestyle Profile spec, and the HEI-2020 National Benchmark Reference. An earlier build of this codebase had drifted from those documents and invented governance and clinical narrative — fabricated IRB/DUA gates, a "Protective Mode"/SCOFF safety mode, a CARDIA long-term trajectory, and an LE8-style single 0–100 "Digital Twin" score — none of which is carried forward here, and none of which this README claims either.

---

## 1. What this app actually is

LLHS is a React Native (Expo Router) mobile app with a FastAPI/MongoDB backend, built for a population research identifies as elevated-risk for disordered eating. That constraint shapes almost every feature below: the app never displays calories, weight, or numeric nutrition targets, never ranks foods "healthy to unhealthy," never shows a raw HEI-2020 number to a participant, and never uses variable/randomized reward mechanics.

**Diet quality comes only from ASA24 recalls, scored with NCI's own HEI-2020 formula.** HEI-2020 (the USDA/NCI 13-component diet-quality index) is never estimated by an LLM or from anything a participant taps or types in-app. Study staff export ASA24's "Totals" file (ASA24 has no API) and upload it on the researcher page; the app scores it with a line-for-line Python port of NCI's published HEI-2020 SAS macro (`backend/hei2020_scoring.py`). The app then compares each component to a fixed national benchmark and turns that comparison into calm, direction-only guidance.

## 2. Core features, as built

### 2.1 Auth & Onboarding
- JWT-based auth (sign-up/login/logout). Anyone with a TAMU email (`ALLOWED_EMAIL_DOMAIN`, default `tamu.edu`) can create an account after confirming the address with an emailed 6-digit code; "Forgot password" works the same way. Logout is real: tokens carry a `jti` claim, and logging out records that `jti` in a `revoked_tokens` collection (TTL-indexed to self-expire) — a leaked token can't be used forever just because a user "signed out" on their own device.
- Onboarding is a **schema-driven Nutrition & Lifestyle Profile survey** (`GET/POST/PATCH /onboarding/profile-survey`) — personalization context (student status, academic major, residence, kitchen access, meal plan, allergies, etc.), explicitly **not** a diet-quality screener. The schema (`PROFILE_SURVEY_SCHEMA`) drives both server-side validation, including `condition`-based skip logic (e.g. kitchen-access follow-ups only shown if the participant has kitchen access), and the frontend's generic section-by-section renderer — the survey's shape lives in one place, not duplicated between client and server.

### 2.2 HEI-2020 from ASA24 (research-facing, not participant-facing)
Everything here needs a signed-in **researcher account** (`POST /research/auth/login` → a `research`-scoped bearer token, 8 h; admins manage accounts via `/research/researchers`, first admin via `python backend/manage_researchers.py add <email> --admin`). The shared `RESEARCH_API_KEY` (`X-Research-Key`) still works for scripts while it's set. Staff workflow: [`docs/ASA24-STAFF-GUIDE.md`](docs/ASA24-STAFF-GUIDE.md).
- **Researcher page** — `GET /research-admin`: ASA24 accounts batch, participants with their food-recall status, links to ASA24 usernames, Totals CSV upload, preview, import.
- **ASA24 accounts batch** — `POST /research/asa24/accounts` (paste `username,password` lines created on the ASA24 researcher site; passwords stored encrypted, never listed) and `GET /research/asa24/accounts` (free / given out, who got which). Each student gets the next free account when they create their LLHS account (or on their next visit if the batch was empty). Parser: `asa24_accounts.py`.
- **Participants** — `PATCH /research/participants/{id}` marks QA/demo accounts (`is_test_account`) so they drop out of cohort counts.
- **Links** — `GET /research/participants`, `PUT /research/asa24/links`, `DELETE /research/asa24/links/{username}` (`db.asa24_links`; one username per participant).
- **Upload** — `POST /research/asa24/preview` (read-only: per-username status `ready`/`unmatched`/`exists`/`not_selected`/`out_of_window` plus warnings for ≠2 recalls, duplicate RecallNo, kcal outside 500–5000) and `POST /research/asa24/import` (stores the selected rows; skips existing unless `overwrite`). Only recalls dated inside that assessment point's window (±1 day) are scored; others are left out with a warning, so one export can't blend several check-ins into one score.
- **Which assessment is current** — the latest *study point* (baseline < check-in 1 < … < check-in 4), not the latest upload, so re-importing baseline can't replace a check-in.
- **Scoring** — `hei2020_scoring.py` ports NCI `hei2020.score.macro.sas` v1.0 (12/11/2024) statement by statement, with derived inputs and the **per-person method (sum all of a participant's recalls, then score once)** from NCI's ASA24 per-person example. Each stored assessment keeps its `summed_inputs` so it can be re-checked in SAS or R `dietaryindex`.
- **Manual import** — `POST /research/hei2020-assessments` still accepts already-scored component values (e.g. from SAS).
- `GET /assessments/hei2020/history` and `GET /assessments/hei2020/focus-candidates` read the data back for the participant.
- **Recall card (participant-facing)** — `GET /asa24/recall` (current point, open/due dates, the student's ASA24 username and password, whether new results are in), `POST /asa24/recall/finished` ("I finished", so staff know when to download) and `POST /asa24/results/seen`. Today shows the card; My Path and Future Me count down to the next recall. A missed window just moves on to the next point — no "missed" message. **Start recall** opens `ASA24_RESPONDENT_URL`.
- **Recall schedule** — `asa24_schedule.py`, counted from the day the student created their account, in the study time zone: baseline due within 7 days, then a check-in every 14 days, open ±3 days. **These are placeholders until the study team confirms the protocol.**

### 2.3 Food, Move & Rest — Health HQ (`GET /domains/food|move|rest`, `GET /domains`)
Replaces the old single 0–100 gauge entirely. The three domains are never combined into one score:
- **Food** — built from the imported HEI-2020 assessment. Each of the 13 components is compared to a fixed national benchmark (NHANES 2017–March 2020, ages 18–25, stored as static constants in `HEI2020_COMPONENTS`) and classified only as **above / below / approximately at** benchmark — a **Population Reference Marker** — never as a raw number, a percentile, or a score out of 100. That marker is shown only for a participant's *strength* components; a component below benchmark becomes a candidate for the Priority Selection flow instead (see 2.4), never a marker.
- **Move** — weekly logged activity minutes.
- **Rest** — average sleep hours, carrying the same confidence tiers as before (manual vs. wearable-sourced), never defaulted to a fake-neutral number when nothing's logged.

### 2.4 Priority Selection Flow (`GET /assessments/hei2020/focus-candidates`, `POST /profile/focus-areas`)
After an HEI-2020 assessment is imported, the participant picks 2–3 "focus areas" themselves from the HEI components that have a meaningful gap below benchmark (`_focus_candidates_from_assessment()`) — the app surfaces candidates, the participant chooses, nothing is auto-assigned. Chosen focus areas drive what Food HQ highlights and what the simulation engine (2.6) can run scenarios against.

### 2.5 My Path (`GET /path`)
A single fixed-appearance avatar/trail visualization (`app/path.tsx`, `PathTrail` component) replacing the old score-arc "Digital Twin." Position along the trail (0–1) advances only through behavioral milestones — meals logged, videos watched, check-ins completed — **never** through a health outcome, a weight change, or an HEI score. There is exactly one visual appearance for the marker; it is not a customizable or randomized avatar.

### 2.6 Deterministic "what-if" simulation
A rule-based scenario engine (`simulate_scenario()`) — not an LLM, not a prediction model — that answers "what would change if I did X more often" for a chosen focus area with **directional, non-numeric** output only. It never invents a point-delta ("+2.3 points") or a projected score; it describes direction and, where honest, magnitude in words, grounded in the actual gap between the participant's imported score and the national benchmark for that component.

### 2.7 Lightweight in-app meal logging (`POST /meals`, `/meals/analyze-photo`, `GET /meals/categories`, `POST /meals/categorize-text`)
A **separate, qualitative** logging layer from HEI-2020 scoring — this in-app logging never feeds or influences an HEI-2020 score, which only ever comes from ASA24. Each meal is tagged with zero or more of nine plain category tags (`vegetables`, `fruit`, `whole_grains`, `refined_grains_starchy`, `beans_fish_nuts`, `other_protein`, `dairy`, `added_sugars`, `salty_processed`) instead of the old pass/fail food-group booleans:
- **Text entry**, with an on-blur `categorize-text` call that auto-suggests categories and flags allergy terms from what was typed.
- **Photo logging** — a vision LLM identifies category tags (not calories) from a photo, with a confidence score; low-confidence identifications require the user to confirm before saving.

Neither path ever surfaces a calorie count, a gram amount, or an HEI-2020 number. Points are capped, not unlimited — meals: 8/day, activities: 6/day, sleep: 3/day, chat: 15/day — logging itself is never blocked once a cap is hit, only the reward stops.

**Voice logging was removed (2026-09).** It only ever worked through Emergent's audio-capable Gemini model; now that TAMU AI is this app's sole AI provider (see 2.14), and neither TAMU IT's own service page nor the team's reference API wrapper (`taugroup/TAMU-Chat-AI`) documents any audio/speech-input endpoint, there's no backend left for it to call. Rather than ship a mic button with nothing behind it, `POST /meals/transcribe-voice` and its frontend recording UI are gone outright — manual text entry and photo logging both remain and both now run on TAMU.

### 2.8 Behavioral Safety Layer (`run_safety_check`)
A reactive pattern detector, not a diagnostic tool and not an onboarding screener. It runs automatically after every meal log and checks the last 3 days of data for two patterns: 3+ skipped meals, or a sustained run (75%+) of small-portion logging. If either fires, it creates a supportive, non-judgmental check-in message — never a penalty, never a lost streak — and de-duplicates so a user isn't shown more than one check-in per 24 hours. This is the only implemented safety mechanism in the app; there is no onboarding eating-disorder screener and no per-user risk flag anywhere in the codebase.

### 2.9 Curriculum & Mini-Games, with Youth Ambassador peer videos (F1/F2)
- **`GET /curriculum`** — a short video curriculum on nutrition literacy, with per-video completion tracking. Each lesson can carry a `peer_video` (Youth Ambassador peer-modeling clip with its own `ambassador_name`, `transition_line`, and `video_url`) shown underneath the baseline lesson once it's been watched, not in place of it.
- **`GET /games`** — scenario-based mini-games, one of which (`g3`, "Build a Balanced Meal") is a real drag-and-drop plate builder, not a quiz.

### 2.10 Drag-and-drop plate building (`/games/ingredients`, `/games/g3/score-plate`)
A real touch interaction (`react-native-gesture-handler` + `react-native-reanimated`) where the user drags food items, grouped by category, from a tray onto a plate. Every draggable item is also tap-to-add — the accessible primary path, with drag as progressive enhancement, since drag-and-drop alone has no equivalent for screen-reader or switch-control users. Scoring (`score_plate()`) returns whether the plate is balanced, which categories are present, qualitative feedback, and a Population Reference Marker — never a numeric score.

### 2.11 Real Texas A&M dining hall integration (Commons + Sbisa)
- **`dining_scraper.py`** talks to the real backing API behind Aggie Dining's public menu site (`apiv4.dineoncampus.com`), using verified location IDs for both halls, and pulls the actual daily menu. Falls back to hand-written sample menus if the live fetch fails for any reason, flagging `"source": "sample"` in the response so the frontend always knows which one it got. **Re-verified live on 2026-10-26** from a real browser: both halls, all three periods, 77–133 items each, same response shape as documented in the module; the exact captured shape is replayed in `tests/test_dining_scraper.py` (13 tests), so the parser stays checked without network access. The scraper now also keeps each item's plain-text `ingredients` and the feed's own qualitative `labels` (allergens such as Egg, Milk, Wheat, Soy; diet labels such as Vegan) — `item_matches_allergy()` checks those as well as the name, so "Brioche Bun" is suppressed for an egg allergy even though its name says nothing about egg. Calories and the nutrient table the feed carries are dropped at the source, never stored or sent to the client. When the periods call already embeds the default period's menu, the second round-trip is skipped.
- **`dining_classifier.py`** tags every real menu item with the same nine lightweight logging categories used everywhere else in the app (`log_categories`), plus the legacy recommendation-tagging fields (`has_vegetables`, `has_whole_grains`, `has_lean_protein`, `high_sodium`, `fiber_level`) that the Plate Composer still consumes — a local keyword-matching engine, deliberately not an LLM call, since neither an LLM nor a research-literature search fits "is this specific dining-hall dish healthy."
- **`plate_composer.py`** generates suggested plate combinations from today's real menu, deliberately not sorted "healthiest first" — it anchors each suggestion in a protein/grain-forward item and rotates sides across suggestions so plates aren't near-duplicates.
- **`POST /dining/chat-build-meal`** — a conversational AI meal-builder grounded only in that day's real menu; anything the model names that isn't actually on the menu is dropped server-side before the response is returned.
- **Allergy-aware suppression** — a participant's allergy terms (`_extract_allergy_terms()` / `filter_items_for_allergies()`) filter what's recommended in dining plates, the ingredient library, and the chat meal-builder. The raw menu-browse view is deliberately **never** filtered, since silently hiding items from the underlying menu is treated as a safety-relevant behavior distinct from what gets recommended.

### 2.12 The "Future Me" coach — full app context, and actions it can propose but never execute unasked
`POST /chat` is personalized from real, current data — not just the participant's focus areas. `build_ai_chat_context()` assembles, fresh on every turn: focus areas and their directional scenario notes, Food's strength areas (direction only), Move minutes and Rest hours/confidence, this week's meal-log count and which of the nine logging categories have and haven't been logged, curriculum/practice-scenario completion, gamification points and streak, My Path's position and remaining milestones, and Wing aggregate progress. Every number in that context is either a plain process-behavior count (already permitted everywhere in this app) or a direction-only Population Reference Marker — a raw HEI-2020 score or national-benchmark value never enters the context at all, since `domain_food()` already strips those at the source. This is what lets the coach answer something like "what am I lagging on" or "what have I logged this week" specifically instead of generically. Since 2026-10-26 the context also carries the participant's **regular foods** from their own logs, the **swap** Future Me's home is showing them, and **where that swap is on today's real menu** (see 2.19), so "what do I usually eat" and "what should I change" get an answer anchored to their actual meals.

The coach can also **propose** — never silently perform — an action when a participant clearly asks in plain language to log a meal, activity, or sleep, to change their focus areas ("log that I had a salad for lunch"), or to try a swap from 2.19 (`try_swap`, which is additionally re-checked against what this participant may be offered at all — focus area, kitchen setup, allergies and dislikes — at proposal time and again at confirm time, so a valid-looking swap id the model made up never becomes a card). The model is not given real tool-calling access to the database; it may only end its reply with one trailing `ACTION_JSON: {...}` line, which is always stripped from what the participant sees and is re-validated server-side against the exact same Pydantic models the manual logging screens use (`MealIn`, `ActivityIn`, `SleepIn`, `FocusAreasIn`) before it's returned to the client as an **unexecuted** `pending_action`. Nothing is written until the participant taps Confirm in the app, which calls `POST /chat/confirm-action` — a separate endpoint that validates the payload again from scratch and writes through the identical shared helper functions the REST logging endpoints use (`_internal_log_meal`, `_internal_log_activity`, `_internal_log_sleep`, `_internal_set_focus_areas`), scoped only to the authenticated participant's own account. A sleep action proposed via chat can never claim a wearable-sourced reading — `_internal_log_sleep` force-sets `source="manual"` regardless of what's in the payload, the same anti-spoofing rule as the manual `/sleep` endpoint (see the #5 security fix in §3). An invalid or hallucinated action (an unknown type, a bad category id) is silently dropped — it never blocks or alters the conversational reply, and dropping it is logged server-side, not surfaced as an error to the participant.

### 2.13 The chat guardrail — the most safety-critical piece of code in this app
`POST /dining/chat-build-meal` and the general coach chat (`POST /chat`) both route through a two-layer output filter before any reply reaches the user:
1. **Numeric pattern matching** — catches formatted (`450 calories`, `20g`) and spelled-out (`two hundred calories`) nutrition figures, and HEI score-fraction leakage (`4.2/10`, `x/13`).
2. **Restriction-language phrase matching** — catches harm that carries no number at all: "watching your intake," "skip the rice to keep it leaner," "guilt-free," and gerund variants of the same ("cutting back," "trimming down").

If either layer fires, the reply is replaced with a fixed, warm, non-blank redirect — never an error, never silence — and any action the model had proposed in that same turn is discarded too, not just the visible text; a turn whose conversational half tripped the guardrail is treated as untrusted end to end. Every block is logged, and three or more blocks within three days from the same user triggers the same supportive check-in as the meal-logging safety detector. This guardrail is tested against a battery of block cases (numeric and worded) and clean edge cases (to check for over-blocking), recorded as a permanent regression test, not a one-time manual check.

### 2.14 TAMU AI — the app's sole, mandatory AI provider (`/settings/tamus/*`)
As of 2026-09, TAMU AI is the **only** LLM backend this app calls — the earlier Emergent-routed default (shared Claude/Gemini access via the `emergentintegrations` library and a single `EMERGENT_LLM_KEY`) has been fully removed, at the team's explicit request. There is no fallback provider any more, which changes the shape of this feature from "advanced/optional" to "required setup":

- **Every participant needs a working TAMU API key before any AI feature responds** — the "Future Me" coach (2.12), photo/text meal-log assist (2.7), and the dining plate review + chat-build-meal assistant (2.11). A student adds their own key (from `chat.tamu.ai`, TAMU's own $5/student AI credit) in Settings; it's encrypted at rest (Fernet symmetric encryption) and write-only — no endpoint ever returns a saved key back to the client.
- **Without a key, every AI-touching endpoint degrades to a clear, safe prompt, never a crash or silent nothing.** `tamus_client.resolve_user_key(user)` is the single place this is decided: it raises `TamusKeyRequiredError` when a participant has no usable key, and every call site (`run_llm`, `llm_vision_call`, dining menu classification) either surfaces that as an explicit "add your TAMU key in Settings" message (the coach, chat-build-meal) or degrades gracefully to manual/deterministic behavior (photo/text categorize-assist falls back to empty suggestions with a `tamus_key_required: true` flag; dining menu classification falls back to the non-AI keyword classifier it already had).
- **A small staff-managed admin/testing exception.** A handful of QA/demo accounts that can't reasonably be expected to hold a personal TAMU credit can be allowlisted by email in `TAMUS_ADMIN_TEST_EMAILS` (comma-separated) to draw from a shared pool of TAU-provisioned keys in `TAMUS_ADMIN_API_KEYS` (also comma-separated, one participant always maps to the same pool key). This is invisible from the app for everyone else, isn't settable from the client, and is meant for staff to hand out sparingly — not a general shared key for the student body.
- **Model choice** stays per-participant (`model_chat`/`model_vision`, from the same catalog as before) but the on/off "enabled" toggle from the old BYOK design is gone — a saved key is simply used.

**Thinking-enabled models (verified 2026-09-24):** TAMU runs its Claude Sonnet/Opus model groups with extended thinking forced on, so Bedrock rejects any `temperature` other than 1 and a `max_tokens` below the thinking budget. `tamus_client.chat()` sends `temperature=1` and `max_tokens ≥ 4096` for those models, and treats TAMU's HTTP-200-with-`error` responses as failures with a readable message. Without this the default chat model (Sonnet 4.6) failed on every call.

### 2.15 Wearable Rest (`/wearable/*`)
Lets a user connect **Fitbit** (primary, per the current architecture deck), Apple Health, or Health Connect so sleep becomes a higher-confidence data source than a manual guess. `POST /wearable/sync-sleep` accepts both `hours` and `activity_minutes` in one call. The plain manual sleep entry always force-sets `source="manual"` server-side regardless of what a client claims — real wearable data can only ever arrive through the dedicated sync endpoint.

### 2.16 Gentle Nudges (`/settings/nudges`)
Opt-in only (off by default), locally-scheduled meal-log reminders (`expo-notifications`) with fixed, calm, pressure-free copy owned entirely client-side.

### 2.17 Weekly Story (`GET /weekly-story`)
A calm, chapter-paged end-of-week recap computed from the user's own real logged data. No numeric score, no "you failed this week" framing.

### 2.18 Social — Wings (`/wings/*`)
Students self-form small groups ("wings") and work toward one shared aggregate goal — never a ranked leaderboard, never visible individual stats. `compute_wing_progress()` only ever returns a single summed number for the whole wing, by construction, not by convention. Photo/text "proof" posting and wing chat/comments are deliberately not built — both are real user-generated-content surfaces that would need a moderation owner before they could ship responsibly.

### 2.19 From your meals — the behavior side of the twin (`GET /future-me` → `from_your_meals`, `GET /future-me/from-your-meals`, `POST /future-me/swaps/{trying|tried|dismissed}`)
Added 2026-10-26. Future Me already knew a participant's focus area (ASA24) and their setup (the onboarding profile). This layer adds what they actually eat, so a suggestion can be anchored to a meal they already have ("the whole-milk yogurt you get most mornings → low-fat yogurt, and it's at Sbisa breakfast today") instead of a generic tip. Three pieces, all deterministic, none of them an LLM:
- **`twin_habits.py`** — a curated food lexicon (plain data the nutrition team can edit; whole-word matching with per-food exclusions, e.g. "veggie burger" is not a burger habit) run over the free-text names and items of the participant's own lightweight meal logs for the trailing 21 days. A food logged in 3+ meals is a "regular", with its usual meal slot. Nothing is claimed until the participant has logged on 3 distinct days; a skipped meal says nothing; an unlogged day is never read as a skipped one. Output is counts of logged meals only — never an amount, nutrient or score — and the evidence is shown to the participant ("You've logged whole-milk yogurt in 5 meals over the last 3 weeks, mostly at breakfast") so they can correct it.
- **`content/swaps.json`** — a reviewable swap table (same `source`/`reviewed` discipline as the Coach's knowledge base; all entries are `reviewed: false` until the nutrition team approves them): 44 entries across the eight focus areas, 35 anchored to a lexicon habit (whole-milk yogurt → low-fat yogurt; white rice → brown rice; soda → sparkling water; chips → fruit or unsalted nuts; bacon → chicken sausage; …) and 9 area defaults for participants with no regular yet (grains + no kitchen → oatmeal, microwave or hot-water). Each carries what it needs (`none` / `microwave` / `stove`), the logging categories it adds (so an allergy that rules out dairy rules out the yogurt swap), and the search terms for finding it on a live menu. Every label and text is checked by a test against the chat guardrail and contains no digits.
- **`twin_suggest.py`** — picks at most two suggestions for one participant: habit-anchored swaps first (most-logged habit first), then one area default; drops anything their kitchen setup can't support, anything their allergy terms or profile dislikes rule out (whole-word matching, so "eggs" blocks the egg swap but not "veggie burger"), and anything they dismissed or tried in the last 14 days; pins a swap they said they'd try. Then it looks the swap up on **today's live Aggie Dining menus** (both halls, all periods, keyword-classified so no TAMU key is needed; the sample menu is never used) and returns up to three matching items with hall, meal and station — the "Find it at Sbisa" button deep-links into Build a Meal with that hall, meal and item already on the plate. `swap_allowed()` is the single authorization check behind every write.

On the Future Me tab this is the "From your meals" card (`src/components/FromYourMeals.tsx`): evidence, the swap, where it is today, "I'll try it" / "Not for me" / "I tried it", and "Ask Future Me about it". The participant's taps are stored per swap in `db.swap_plans` (latest status wins) and only ever for their own account. The Coach reads the same block (2.12). Cold start is explicit: "Log on 2 more days and I'll start noticing your regulars."

**Two engines, kept side by side for the testing phase (`TWIN_ENGINE`, `twin_llm.py`).** The rules engine above is one way to make these decisions; the team also wanted to see what TAMU AI does with the same inputs before converging on one. The AI engine may do exactly three things, each re-verified server-side: (1) read the raw meal-log text and name the participant's regulars in their own words — this is where it beats the lexicon ("Chobani Flip" needs no table entry) — citing the logged meals that support each one, which the server re-counts itself (whole-word grounding, 3+ meals, guardrail-checked name); (2) pick among the swaps this participant may be offered at all (`swap_allowed`: focus area, kitchen setup, allergies, dislikes), never write one; (3) name today's menu items exactly as served, anything else dropped, every item re-filtered for allergies; plus one short "why" sentence that goes through the chat guardrail and is dropped if it names an allergen, a dislike, a hall, or contains a digit. The verified model output is cached per day until the logs, focus area or menus change; everything safety-relevant (allergies, dislikes, kitchen, "Not for me"/"I'll try it") is re-applied on every read, so a cached pick never outlives a newly declared allergy. Without a key, or when the call fails, the participant sees the rules engine (a failed call rests for five minutes, a missing key is re-checked on the next read). Whenever the AI engine runs, both engines' decisions are stored in `db.twin_decisions` (one row per participant per day); the researcher page's section 8 shows them side by side with a top-swap agreement rate and a regulars-overlap rate (`GET /research/twin-decisions`, `/summary`, and `POST /research/twin-decisions/recompute` to run both engines for one participant on demand). Participants never see a toggle.

### 2.20 The behavioral twin — diet, activity and sleep in one profile (`GET /twin`, `/twin/*`, `GET /future-me` → `twin`)
Added 2026-11-11 (see [`docs/CHANGELOG-2026-11-11.md`](docs/CHANGELOG-2026-11-11.md)). The study team's direction after 2.19: one participant-specific profile across the three behavioral components of AHA Life's Essential 8 — diet, physical activity, sleep — **never combined into a score**, built from (1) ASA24 and lightweight meal logs, (2) tracker and manual activity and sleep, (3) what the participant tells us (onboarding profile, answers, circumstances), and (4) how earlier steps went and why. Its first rule is **ask, don't assume**:
- **`twin_patterns.py`** notices *possible* patterns over 21 days — quieter weekdays or weekends for movement, irregular bedtimes, shorter sleep before class days, explicitly skipped weekday breakfasts, meal regulars, and one pattern across domains (a weekday squeeze) — each with evidence in counts and a question. Nothing is used until the participant says Yes / Sometimes; "Not really" isn't asked again for 28 days. A meal regular must be confirmed before its swap is offered.
- **`twin_recommend.py` + `content/twin_library.json`** choose one or two steps from 44 reviewed-pending items (add, modify, grocery, routine, plan; each tagged with BCT Taxonomy v1 techniques, contexts, fits, needs, cost, effort, coping plans) plus the swap table, by readable rules: hard filters (focus area, confirmed pattern or opt-in, where they eat, kitchen, allergies, dislikes, recent "Not for me", stated constraints, safety pause), then scoring (confirmed pattern, stated circumstance, main eating context, respected constraint, technique that worked, a different approach after one didn't fit). Every step shows **Why this**, built only from those factors. Dining-hall menus are shown only to dining-hall eaters; others get grocery, home or takeout versions.
- **`twin_profile.py`** keeps the profile (`db.twin_facts`, `db.twin_plans`, `db.twin_events`): reasons for "Not for me" / "Didn't fit" (Too expensive, Doesn't fit my schedule, Not available where I eat, …) become constraints every later step respects; steps that worked move to **Keep going** with a later check-in; "What I've learned about you" lists every fact with its source, each removable. TAMU AI only maps a free-text note onto the fixed lists when no keyword matched.
- The Coach sees confirmed facts, unconfirmed patterns (labelled so it asks rather than asserts), constraints and the twin's steps, and can propose `try_step` (re-checked at proposal and confirm). A safety check-in in the last 14 days pauses food and exercise steps.
- Staff: researcher page section 9 (`/research/twin-profile`, `/research/twin-snapshots/rate`, `/research/twin-eval`) — pattern accuracy from participants' own answers, appropriateness from staff ratings, constraint adherence and feedback incorporation from daily snapshots (`db.twin_snapshots`).
- Wearables: `POST /wearable/sync-sleep` accepts `sleep_start`, `sleep_end`, `steps` and upserts per date; `POST /wearable/sync-days` takes up to 31 days; manual sleep accepts optional `bedtime` / `wake`.

## 3. Security & data-integrity hardening

| Protection | What it actually does |
|---|---|
| **Rate limiting** | `slowapi`, per-IP: `/auth/login` (10/min), `/meals/categorize-text` (20/min), `/settings/tamus/test` (10/min), `/dining/chat-build-meal` (15/min), `/dining/review-plate` + `/dining/sbisa/review-plate` (15/min), `/chat` (15/min), `/chat/confirm-action` (20/min), `/meals/analyze-photo` (15/min). |
| **Chat-action re-validation** | Any action the coach proposes is re-validated against the same Pydantic models as the manual endpoints, twice — once when the model proposes it, again when the participant confirms it — and can only ever write to the confirming participant's own account. |
| **JWT revocation** | Real server-side logout via a `jti` + TTL-indexed revocation collection (see 2.1). |
| **CORS** | A real origin allowlist (`CORS_ALLOWED_ORIGINS`), not a wildcard. |
| **Input size limits** | Every user-supplied field that reaches an LLM prompt or gets stored has an explicit length/size cap. |
| **Points-farming caps** | Described in 2.7 (`DAILY_POINT_CAPS`). |
| **Research-import gating** | Every `/research/*` endpoint (manual HEI import, ASA24 accounts/links/preview/import, participant list) requires a researcher sign-in, or the optional shared `RESEARCH_API_KEY` sent as `X-Research-Key`. The `/research-admin` page itself is static HTML and holds the key only in that tab's sessionStorage. Staff sign in with individual researcher accounts (bcrypt, `research`-scoped tokens that participant endpoints reject and vice versa, admin/staff roles, disable = immediate lockout); imports record who ran them. |
| **Mongo indexes** | Hot-path queries (`user_id` + `created_at` lookups, unique indexes on user email/id, join codes, revoked-token lookups) are indexed. |
| **Cohort math** | The Wings-adjacent global cohort counter (`GET /cohort`) is computed live and correctly scoped per-user, per-week. |

## 6. Environment variables

| Variable | Purpose | Behavior if unset |
|---|---|---|
| `MONGO_URL`, `DB_NAME` | Database connection | Required — app won't start without these |
| `JWT_SECRET` | Token signing | Falls back to an insecure dev default, logs a warning |
| `CORS_ALLOWED_ORIGINS` | Web-build CORS allowlist | Falls back to localhost-only, logs a warning |
| `TAMUS_KEY_ENCRYPTION_SECRET` | Encrypts stored TAMU API keys | Falls back to an insecure dev key, logs a warning |
| `TAMUS_ADMIN_TEST_EMAILS` | Comma-separated allowlist of staff-managed QA/demo accounts that draw from the admin/testing key pool instead of needing a personal TAMU key (see 2.14) | Empty — no account gets pool access; every participant needs their own key |
| `TAMUS_ADMIN_API_KEYS` | Comma-separated pool of TAU-provisioned TAMU keys for the accounts above | Empty — allowlisted accounts still can't use AI features until this is set |
| `TWIN_ENGINE` | Which "From your meals" engine participants see (2.19): `rules` (deterministic lexicon + swap table) or `llm` (TAMU AI names regulars from the raw log text and picks among the same vetted swaps and real menu items, re-verified server-side; falls back to `rules` without a key). Both engines' decisions are recorded for comparison whenever the AI engine runs | Defaults to `rules` |
| `TWIN_ONLY_REVIEWED` | `true` limits the behavioral twin (2.20) to library steps and swaps whose `reviewed` flag the nutrition team has set | Off — every step is offered while the library is under review |
| `RESEARCH_API_KEY` | Optional shared-key fallback for `/research/*` (scripts, bootstrap) | Only researcher sign-ins work, logs a notice |
| `RESEARCH_TOKEN_HOURS` | Researcher session length | Defaults to 8 |
| `RATE_LIMIT_ENABLED` | Set `false` only for local/CI test runs (the suite signs in far more often than the per-minute limit) | Defaults to on |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `EMAIL_FROM` | Email account that sends the Create account and Forgot password codes (e.g. a study Gmail with an app password: `smtp.gmail.com`, port `465`) | Unset: on Vercel, Create account and Forgot password say email isn't set up yet; locally the codes are written to the server log |
| `ALLOWED_EMAIL_DOMAIN` | Which email addresses can create an account | Defaults to `tamu.edu` |
| `ASA24_RESPONDENT_URL` | Where **Start recall** sends students — set it to the study's ASA24 respondent login link | Defaults to the general ASA24 site |
| `ACCESS_TOKEN_MINUTES` | JWT lifetime | Defaults to 14 days |
| `COHORT_DEMO_SEED` | Cosmetic offset for demo/pitch deployments of the cohort counter | Defaults to `0` — a real deployment shows honest numbers unless deliberately overridden |

All "insecure fallback" variables above log a clear warning on startup naming exactly what's wrong — this app does not fail silently on a missing production secret. There is no `EMERGENT_LLM_KEY` any more — TAMU AI is the app's only LLM backend (2.14), and every participant needs their own TAMU key (or admin/testing pool access) for AI features to respond at all; there is no shared default to fall back to.

## 7. Deployment (live at https://llhs.vercel.app)

One Vercel project (`llhs`): the Expo web build is served as static files and `backend/server.py` runs as a single Python function at `/api` on the same origin, backed by MongoDB Atlas. Deploys are manual — pushing to GitHub does not deploy.

```bash
git fetch origin && git checkout --detach origin/main      # deploy only what's merged
(cd backend && python -m pytest tests -n 0 -q --ignore=tests/backend_test.py)
./deploy/vercel/build.sh                                  # assembles .vercel-deploy/
cd .vercel-deploy && npx vercel --scope <team> deploy --prod --yes
```

`build.sh` exports the web app to `public/`, copies the backend modules, `backend/content/` and `research_admin.html` into the function, and renames Expo's `assets/node_modules` to `assets/vendor` (the Vercel CLI skips `node_modules` folders, which would drop the icon fonts). Settings (section 6) live in the Vercel project's Environment Variables; a change only takes effect after the next deploy.
